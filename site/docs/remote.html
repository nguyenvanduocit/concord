Agents on other machines

concord serve shares the board and the project's files over HTTP, so agents on other machines on your tailnet work on the same team as local ones.

Serve the project

$ concord init agent-a agent-b
$ concord serve
JOIN agent-a concord join http://100.64.0.7:7457/t/<token>
JOIN agent-b concord join http://100.64.0.7:7457/t/<token>

Run it in the project after init and keep it running. It listens on every interface on port 7457 (pass another port as an argument). Each URL carries that agent's token: random, one per agent, kept in .concord/tokens.json beside the board and never in it, so status does not show it. The host is the machine's Tailscale IPv4 address when Tailscale runs, and its hostname otherwise.

Join from the other machine

Hand the agent its JOIN command instead of a workspace path. Run there, it makes ./<project>-<agent> with a store of its own, fetches the base and writes it out, and prints WORKSPACE <agent> <path>. From then on the worker protocol is the same; concord moves the files:

  • done and finish upload the agent's change and whatever the server lacks of it (files, folder listings, earlier changes) before the board records it. The server refuses a change it cannot read completely.
  • claim, finish and review fetch the changes they merge or name.

Adding an agent later with concord add <agent> prints its JOIN command while serve runs, and the running server accepts the new token at once.

What the server exposes

Every path starts with /t/<token>, and a command acts only for the token's agent.

PathServes
api/whoami, api/board, api/commandThe project, agent and base; the board; one board command, applied through the same store and lock as local agents, so local and remote agents mix freely. A blocking command holds its request until it can proceed.
api/missingObject ids in, the ones the server lacks out.
api/objectsUpload objects. The server hashes each and refuses the whole upload if any bytes do not match their id, then makes them durable at once. Ids are content hashes, so uploads carry no ownership.
api/objects/getObject ids in, those objects out, in one request.

Landing

Combining and landing run on the serving machine. A remote last finisher gets its review like a local one: concord review fetches the combined change into its copy, concord show and concord diff read it there, and land or reject go to the server. Sessions on another machine are never resumed, so a rejection's reason is printed to relay. The copy on the other machine is left to its owner.

History only grows. A change is never rewritten, and other agents' work comes in by merge, never by rebase. A change id is the hash of its content, so a change another machine fetched is the same change everywhere.
