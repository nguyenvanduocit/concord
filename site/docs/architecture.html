How it works

concord has three parts: a board that every agent reads and writes, a file store of its own that gives each agent a separate folder, and a landing step that combines their work and has the agents review it before anything lands.

The stack

LayerChoiceWhy
Isolationone folder per agent, written out from concord's own storethe protocol needs five file operations, nothing more; no version control to set up or to collide with yours
Coordinationthe concord boardthe only layer that prevented semantic bugs
Merge driverMergiraf, on every file both sides changedresolves same-function conflicts a line merge cannot; merges any text line by line where it has no grammar; Weave lost the ConflictBench A/B
Landingcombine and mechanical checks in concord, review by the team's agentstests are written by the same agents; a reviewer reading each agent's criteria decided every case the tests decide

The board

The board is one JSON file, state.json, in the project's .concord/ folder. Every agent workspace has a .concord/workspace.json naming the project's store, so any workspace or subdirectory reaches the same board, and each project has its own. Every command checks and changes the board inside one exclusive flock.

A blocking command that has to wait releases the lock and retries every 2 seconds. The board records each agent's last command, and a waiting command refreshes its own agent's record at most once a minute. That record is how concord tells a slow agent from a crashed one: 30 minutes of silence stops the wait with BLOCKED by <agent>.

The store

concord keeps its files itself. What the protocol does with files is five operations, so that is all the store does:

Protocol stepStore operation
a workspace starts at the base (init, plan, add, join)materialize a change into a folder
done, finish, before any mergesnapshot a folder into a change
claim (LATEST), finish (exit 10)merge other changes into a folder, three-way, per file
combining a round; landing it in your foldermerge
agents on other machinessync missing objects by hash

Everything is content-addressed with BLAKE3 under .concord/objects/ and immutable: a blob is a file's bytes, a tree maps sorted paths to blobs, a change is its tree, its parents, its agent and a message. A change id is the hash of the change, so the same change has the same id on every machine. There are no branches, refs, rebases or operation log; the board names every change that matters. Each object is written to a temp file, synced and renamed into place before anything points at it.

A snapshot honours .gitignore and .ignore files whether or not git is present, skips .concord, .git and .jj, and tracks everything else, so no agent's new file is left behind. A stat cache makes it hash only changed files. Your project folder is never an agent's workspace, so a session editing there without concord keeps its files, and those edits enter the next round.

History only grows. A change is never rewritten, and other agents' work comes in by merge, never by rebase.

Merging

Per path: unchanged on one side takes the other; the same on both sides is kept; changed on both goes to Mergiraf (mergiraf merge, conflict markers on exit 1). A symlink, a file that is not UTF-8, or a clash with a file already on disk keeps ours and writes theirs next to it as <path>.theirs. A file one side deleted and the other changed stays, listed as a decision. Several merge bases after criss-cross merges are first merged into a virtual base, as git's recursive strategy does.

Rust architecture

A functional core with an imperative shell around it:

ModuleRole
corePure state machine: apply(Option<Board>, Command, now) -> Result<Step, Error>, where Step is Wait or Next(Board, Outcome). Barrier, queue order, idempotent plan, seen-set for contract notices. Every protocol rule lives here and is tested without a filesystem or processes.
objectsThe object store (blobs, trees, changes by BLAKE3 id; batched durable writes) and the pure change-graph helpers: ancestors, lowest common ancestors, heads.
worktreeA folder's .concord state: snapshot, materialize, commit, merge in, pull.
mergeplan, pure and per path, and apply: Mergiraf, .theirs files, the conflict list.
diffThe unified diff concord diff prints.
storeThe board under flock, durable atomic writes, the ledger, and which folder a command runs in.
teamThe project folder, the base snapshot, agent workspaces.
gateCombine (lost-work check, merge of the tips, review checkout), land, discard, the ledger entry.
serve, remoteThe HTTP server (board API, object sync) and its client in a joined copy.
cliArgument parsing, waiting loops, exit codes. The concord binary calls concord::main.

Open decisions

  • Structured contracts (proposed, not built): done takes --sig, --renamed-to, --was, --now and --callers in place of a free-text note. concord copies the signature lines from the agent's file itself, and --now asks for a value seen by running the code, so "now always float" cannot be left vague or wrong.
  • Stable function identity: claim keys follow renames, so total and subtotal are the same entity.
  • A speedup scenario: five or more agents on a real repository where most tasks are independent, to show the board does not over-serialize.
  • Delivery: the CLI ships with an agent skill; an MCP server is the remaining option.
  • Review with real agents: LLM agents writing their own criteria at plan, then the ConflictBench merges Mergiraf got wrong and right, with the rule set before the run.
