Worker protocol

Every agent follows the same four steps. After plan, an agent runs everything inside its own workspace and edits files only there; concord knows who it is from that folder.

The steps

  1. Plan before editing anything. concord plan <modifies> <uses> -- <done when ...>, with comma lists and - for none.
    • modifies: every existing function, type or method whose code you will touch, even if its signature stays the same.
    • uses: existing functions you call whose behavior your code depends on.
    • After --: your done-criteria, what must be true of your own change. Another agent checks your work against exactly these, by reading it. State contracts with concrete values (subtotal(ITEMS, discount_pct=20) == 20), not a story ("discount works").
    Without a workspace yet, run it from anywhere in the project. It joins you under a free name, or the name from your brief (concord plan <name> <modifies> <uses>), and prints WORKSPACE <name> <path>. Move there and work only there. Running plan again replaces your plan; the reviewer still sees your first criteria next to changed ones.
  2. One function at a time. Touch no file until claim has printed CLAIMED. For each function in modifies:
    • concord claim <fn> waits for your turn. If another agent changed the function before you, it prints that agent's note after LATEST and has already merged the change into your workspace (MERGED). CONFLICTS <files>: settle those first. Remove the conflict markers; for a <file>.theirs (the other side of a binary file or symlink, or a file that clashed with one you already had), put the right content in <file> and delete the .theirs file. A file one side deleted and the other changed is kept: keeping it or deleting it both settle it.
    • Edit, run the tests.
    • concord done <fn> "<contract note>" records your work so far as a change. You never commit yourself.
    Finish one function with done before you claim the next. Holding two claims can deadlock the team. done and finish refuse while a conflict marker or a .theirs file remains.
  3. Finish. concord finish records leftover work and waits until nobody else holds or queues a function you use.
    • Exit 0, FINISHED: report it.
    • Exit 10, NEW CONTRACT CHANGES: functions you use changed, and those changes are already merged into your workspace. Settle any CONFLICTS, adapt your code to every note, re-run the tests, then run concord finish again.
    • Exit 11, WAITING for ...: others are still working. Run the same command again.
    • Exit 12, REVIEW REQUIRED: you finished last. Review the round before you report (below).
    • Exit 1, FAIL the round cannot be combined: an unresolved conflict between agents' work, or an empty finished change (work lost). Fix it in your workspace, then finish again.
  4. Review (exit 12; concord review prints it again). The combined result is checked out in the folder after COMBINED ... checked out at. concord show <change> [<file>] prints a change's files or one file, and concord diff <base> <head> an agent's own work. Check each agent's criteria against that agent's own work, and the combined result against every contract change: is every caller adapted? A criterion is met only if the code, as written, satisfies it exactly. Then concord land "<evidence per criterion, file:line>", or concord reject <agent> "<what is wrong, file:line, what would satisfy it>". Resumed with a rejection: fix exactly that, then concord finish.

Waiting and blocked agents

claim and finish wait at most 100 seconds per call, then exit 11 with WAITING for .... Run the same command again. The limit keeps each call inside an agent tool's command timeout (Claude Code kills commands after 2 minutes by default), where a killed wait would look like a failure.

Waiting continues as long as the agents it waits on are alive. When one of them has run no command for 30 minutes, the wait stops with exit 1 and BLOCKED by <agent>. Run concord status; if that agent crashed, concord release <agent>, then retry. A silent agent is reported, never stripped of its claim: editing one function for a long time is normal.

Writing a contract note

The note is all a caller sees. Write the new contract, not the story:

<name>(<params>) -> <return type>: <behavior>; CHANGED: <what callers must do differently>
  • Renamed: subtotal(items) -> int: sum of price*qty; CHANGED: renamed from total
  • Type change: subtotal(items, discount_pct=0) -> float; CHANGED: now always float, format before printing

"Returns a number" is not a contract: a caller cannot tell that the result became a float.
