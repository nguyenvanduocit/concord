Findings

What was tested and measured, and where each design choice comes from. The cart scenario ran on 2026-11-18 on macOS with jj 0.47.1, GitButler 0.23.4, Mergiraf 0.20.0 and Python 3.12. Agents were Claude Haiku subagents. Each setup ran once on a scenario built to collide, so these results show failure modes, not frequencies.

The cart scenario

cart.py has total(items) and item_count(items). Three agents start from the same base, none told about the others:

AgentTaskCollides with
Arename total to subtotalB (same function), C (C calls it)
Badd discount_pct=0 to totalA (same function); its formula makes the result a float
Cadd receipt() calling total; its test expects "3 items, total 25"A (name), B (the float prints 25.0)

A correct combined result passes 4 tests. Two of the bugs are invisible to text merging: the rename merges cleanly while the caller still calls total, and the float causes no textual conflict at all.

What each layer is worth

  • A combined-test gate before landing is the only thing that detected every semantic bug. Every setup without it landed broken code.
  • Coordination prevents semantic bugs instead of only detecting them. The first version missed the float because C finished before B announced it. A plan barrier (all intents known before work) and a blocking finish that returns exit 10 fixed it: C switched to subtotal and formatted the float.
  • Structural merging with Mergiraf resolves conflicts inside one function. It does not resolve two top-level functions appended at the same spot, in git or jj.
  • The version-control tool changed merge flow, not correctness: jj kept merges from blocking where git stopped, and both landed the same broken code without coordination.

Known gaps

  • B's note said "returns int|float … a number" instead of "now always float". C caught the float by reading code, not from the note. Free-text notes are too weak; structured contracts are an open decision.
  • The claim key is the original name: B's done subtotal was rejected. Keys must follow renames.
  • The board serializes agents that touch the same function, so this scenario shows correctness, not speedup.

Dogfood: concord developing concord

Three Claude Sonnet subagents, one workspace each, briefed only with the concord skill, their task and their scope, built three features of concord itself. Two of them planned to modify the same function: the second waited, claimed after the first one's done, and got its change merged in before editing. The gate passed on the first run with clippy clean and 25 tests passing.

The run showed two gaps in the skill, both now stated in it: an agent first planned modifies=- for a function whose body it changed, and edited before claiming. Docs are not functions: all three would have edited the design doc in parallel, so the orchestrator kept docs to itself and edited them after the gate.

concord's own store

concord now keeps its files itself: BLAKE3 objects in .concord/, Mergiraf on every file both sides changed, no jj and no git. The four end-to-end experiments pass on it unchanged in what they check:

  • Cart scenario: the combined code is byte-identical to the recorded 4/4 result. The landed round is two uncommitted edits (cart.py, test_cart.py) and git's HEAD did not move.
  • Landing: with uncommitted work in a git repository, an approved round arrives as uncommitted edits, the user's edits from before and during the round survive, and every file under .git has the same checksum before and after. A rejected round leaves every file of the folder as it was.
  • Remote agents: a joined copy fetches the base and another agent's change by hash, uploads its own, and a remote agent reviews and approves. The server refuses an object whose bytes do not hash to its id.
  • Self-join: a busy session's draft in the project folder, and every line it appended, survive two rounds.

Found on the way: two finishes at once could both combine the round. The board is now read under the combine lock; the landing experiment reproduced the race before the fix and ran 3 of 3 clean after.

Store speed, release build, 10 000 files of 3.9 KB (39 MB) on an external APFS drive, one run each:

OperationTime
first snapshot, every object new41.7 s
snapshot, no new objects, stat cache cold0.44 s
snapshot, stat cache warm0.12 s

About 65% of the first snapshot is the fsync of each new object. The steady state (done, finish: a few changed files) is fast; creating a workspace or a review checkout writes every file, about 1.4 ms per file on this drive. Not measured: an internal SSD, or parallel writes.

Public benchmarks: merge tool A/B

ConflictBench: 159 real Java merge scenarios. A pass means the merged files equal the developer's resolution, text for text.

Gate merge toolsPassConflictWrong
plain git merge-file (2 cases error)01570
Mergiraf2710626
Mergiraf, then Weave378537

Weave turned 21 conflicts into merges: 10 equal the developer's resolution and 11 differ. Of those 11, 3 were equivalent, 3 kept both sides harmlessly, and 5 were broken, including code that does not compile and a dropped parameter. The rule set before the run was to keep Weave only if passes rose without wrong merges rising. It failed, so the gate uses Mergiraf alone. "Wrong" means text inequality, so some wrong merges are fine code; the column compares tools, it does not count bugs.

Agent review instead of tests

Can landing hand the verdict to an agent instead of running the project's tests? The cart scenario's combined code in six variants went to a reviewer with no tools, given each agent's done-criteria, the contract notes and the code, answering LAND or REJECT <agent>. Claude Haiku and Sonnet, 5 runs per case, the rule fixed before each run, truth from the four tests plus hidden checks.

RunCriteria read againstMain bugs rejectedCorrect code landedBug the tests miss, rejected
1combined code30/30Sonnet 5/10, Haiku 5/10(case labeled correct)
2combined code30/30Sonnet 10/10, Haiku 6/10Sonnet 2/5, Haiku 4/5
3each agent's own head30/3020/20Sonnet 0/5, Haiku 2/5
  • The bug the test gate existed for, the float behind B's vague note, was rejected 30 of 30 times, without running code.
  • Criteria describe one agent's change. Read against the combined code, another agent's declared change "breaks" them, and Haiku rejected correct code 3 of 5 times for it. Read against each agent's own head: no false rejections. concord's review uses that scope.
  • A bug no criterion names is found by chance (:g prints 1234567 as 1.23457e+06), and the tests miss it every time. A reviewer is as good as the criteria, so the skill makes agents state them as contracts.

External evidence

From a 2026 literature review: claims extracted from 22 sources, each checked by three independent verifiers, kept only if at least two upheld it. Almost all agent-era data comes from single 2026 arXiv preprints, not replicated: the numbers show failure modes, not settled rates.

  • Free-text coordination fails (CooperBench): two agents splitting a pair of tasks succeed about 30% less often than one agent doing both (GPT-5, 315 to 183 over 600+ task pairs). In 50 failed traces the causes were wrong beliefs about the other's plan (42), broken commitments (32) and communication (26). Turning chat off made no significant difference. The agents had no shared workspace, so a board like concord's is untested there.
  • A stale base causes conflicts that claims cannot (2610.04779): 47.3% of conflicts between agent PRs happened although the two PRs edited different files. All 48 that could be reconstructed merged cleanly on a shared base. concord merges LATEST at claim and unseen contract changes at finish for this reason.
  • A clean merge proves nothing (2609.25396): when one agent changes an interface another uses, the combined code failed in 97% of constructed runs. This supports a check on the combined result.
  • Isolation beats a shared directory (2603.21489): separate worktrees 63.3%, soft isolation in one directory 55.5%, one agent 57.2% on PaperBench. This agrees with the GitButler result above.
  • Structured merge trades one error for another (ASE 2019): semistructured merge reports more false conflicts (36 vs 4), structured merge misses more real ones (39 vs 5). Either way, something has to check the combined code after the merge tool.
