## New Agentic-Centric Version Control Systems

Agentic-centric version control systems redesign code storage, branching, merging, and provenance around autonomous AI coding agents rather than human developers typing at a keyboard. Instead of assuming full local repository clones, manual line-by-line staging, human-paced pull requests, and after-the-fact commit messages, these systems optimize for high-concurrency task isolation, virtual or server-resident working trees, structural or graph-based conflict resolution, and first-class capture of prompts, reasoning traces, and tool calls.

Across 2025 and 2026, four distinct architectural paths have emerged to address agent-scale bottlenecks: ground-up agent-native or centralized online VCSs (**Oak**, **Anthropic Scion**, **Atomic**, **Drift**); rebuilt Git-protocol backends and agentic hosting forges (**OpenAI Pando**, **Entire**, **Cursor Origin**); Git-compatible local workflow layers and tree-sitter semantic merge drivers (**Jujutsu**, **GitButler**, **Sapling**, **Weave/Sem**, **STORM**); and copy-on-write (CoW) workspace sandboxes paired with versioned agent state databases (**git-cow**, **SandFS**, **Dolt/Beads**, **GitOfThoughts**).

Three practical caveats govern adoption as of November 2026. First, while vendors and hyperscalers report dramatic speedups and infrastructure reductions, independent cross-platform benchmarks remain scarce, and two of the highest-profile systems (**Scion** and **Pando**) remain internal to their creators. Second, non-Git tools incur an "LLM prior tax," because frontier models pre-trained heavily on Git frequently fall back to standard `git` commands unless constrained by harness wrappers, Model Context Protocol (MCP) tools, or strict rule files. Third, eliminating repository I/O latency does not cure downstream bottlenecks: when agents generate patches faster than teams can inspect them, waiting time simply shifts from source control to code review and continuous integration (CI) queues.

## Why Human-Centric Git Breaks Under Agentic Workloads

Traditional distributed version control systems (DVCS) like Git were architected in 2005 around human cognitive pacing: a developer maintains a durable local clone, intentionally stages hunks, writes a retrospective commit message, and opens a modest number of pull requests per week. Parallel coding agents invert those operating assumptions across merge semantics, server concurrency, and change provenance.

Empirical evidence shows that autonomous pull requests carry elevated integration risk. In the 2026 **AgenticFlict** study, researchers collected over 142,000 agent-authored pull requests across 59,000+ GitHub repositories and deterministically replayed 107,000+ of them through merge simulation. The pipeline recorded a **27.67% textual merge conflict rate** (more than 29,000 conflicted PRs spanning 336,000+ conflict regions)—notably higher than the 10–20% range typically reported in prior studies of human-authored PRs, even though the dataset captures syntactic overlaps only and does not include an internal matched human baseline. Complementary analysis of agentic PRs organizes multi-agent interference into three sequential dependency layers: **Layer 1 (Textual Conflicts)** from overlapping line edits or structural modify/delete collisions; **Layer 2 (Build Conflicts)** where Git's line-based `diff3` merges cleanly across files—such as one agent adding a required function parameter while another calls the old signature—yet yields a broken Abstract Syntax Tree (AST) at compilation; and **Layer 3 (Semantic Conflicts)** where merged code compiles without error but violates cross-module execution invariants.

At hyperscale, Git's decentralized architecture and repository-wide ref coordination create acute infrastructure failures. Standard Git servers serialize repository-wide reference updates and advertise all refs on connection; when automated fleets spawn millions of ephemeral branches, the advertised ref list alone can exceed **100 MiB** before transferring any code. At **OpenAI**, Codex-driven parallelization caused pushes, fetches, and merges on its monorepo to contend, pushing supporting-system reliability **below 90%** at times. At **Anthropic**, daily monorepo merges surged more than tenfold from roughly **2,500 per day** in May 2026 to over **30,000 per day** in September 2026 (peaking at 30,401 on September 9), while CI runners demanded roughly **25 million checkouts per day** against a monorepo with nearly 100 GB of `main` history and an over-25 GB compressed working copy—an estimated **600+ PB/day** if fetched naively. Even at smaller team scales, GitHub's REST API limit of 5,000 requests per hour per token can be exhausted within minutes by shared agent fleets.

Finally, Git records *what* changed while discarding *why* it changed. Prompts, discovered schema or library constraints, rejected architectural alternatives, tool-call sequences, and token costs vanish when an agent session terminates or compacts its context window. Without persistent causal provenance, subsequent agents waste tokens reverse-engineering intent from raw diffs, and human reviewers lack the audit trail needed to verify compliance or catch silent architectural erosion.

Because engineering organizations hit different bottlenecks first—ranging from local merge collisions and sandbox startup overhead to monorepo server saturation and compliance auditing—new agentic VCS platforms diverge sharply in how far they depart from Git.

## Deep Dive Into the Four Architectural Paths

### Ground-Up Agent-Native Substrates and Centralized VCS

The most radical entrants discard Git's local object store and line-diff model altogether, contending that agent workflows require either centralized, server-managed state or mathematically commutative change graphs.

**Oak** (`oak.space`), introduced in June 2026, replaces full repository clones with **virtual mounts** backed by operating-system virtual filesystem interfaces: **FSKit** on macOS 26+, **FUSE** on Linux, and **Projected File System** on Windows x86\_64 (though early Show HN disclosures noted a Windows build was not yet shipped). Running ten parallel agent sessions opens ten lazy mounts over a server-side source of truth, fetching files on demand rather than materializing ten full checkouts. Oak enforces five opinionated workflow rules: a branch represents a single task (`oak init` and `oak clone` place sessions directly on a fresh personal branch); `oak commit` acts as a checkpoint without a `-m` flag because intent is documented once per branch via `oak desc`; `main` resides strictly on the server; merges require human authorization and **squash-on-merge** into one commit per task; and finished work exports to Git for downstream compatibility. Oak's creators claim snapshots up to 95% faster than Git on targeted workflows, 90% faster per-operation execution, and 50% fewer VCS-related tokens, but third-party benchmark suites are pending and the platform currently lacks CI and issue tracking.

**Anthropic Scion**, detailed in October 2026, addresses hyperscale monorepo saturation rather than local ergonomics. Built and deployed in five months by a seven-engineer team alongside a custom code-review tool (**Antique**), Scion explicitly drops Git's offline-first design—assuming that clients (primarily Claude agents and CI jobs) are always online. Commits, merges, and rebases run lock-free on the server via compare-and-swap (CAS) operations on a single Spanner row, eliminating packfiles and discouraging branch refs outside `main` and release branches. Its four-tier topology—the `scn` client, node-local `scion-daemon`, regional `scion-cache`, and authoritative `scion-server` —speaks a uniform RPC protocol and exposes source-control queries (`blame`, `diff`, `bisect`) directly via API so CI jobs frequently require no local checkout. Derived metadata structures are defined recursively from parent changesets, allowing eager or deferred computation. Relative to its former fleet of hundreds of Git mirrors, Anthropic reports a **200x smaller** CPU and memory footprint, checkouts reduced from minutes to seconds, cache hit rates exceeding 99%, and a **25% CI CPU capacity gain**. AI also accelerated Scion's construction: an internal preview of Claude Mythos reportedly rewrote its Git-to-Scion ingestion pipeline to run 4x faster with 20x less memory.

**Atomic** (`atomic.dev`) and **Drift** (`sebhaan/drift`) focus instead on semantic representation and causal provenance. Drawing from Pijul and Darcs patch theory, Atomic stores repository state in a `redb` CoW B-tree as a **dual-layer graph**: a mathematical `HashedChange` graph layer (recording predecessor and successor byte contexts so independent edits commute) paired with a semantic layer (`Trunk` for inode-tracked files, `Branch` for lines, and `Leaf` for tokens). This structure lets concurrent edits to different tokens on the same line—or a file rename paired with an in-file edit—compose cleanly without textual conflicts while supporting `O(1)` token-level blame. Agents work in isolated **draft views** (filtered perspectives over one canonical graph rather than copied directories) and emit signed provenance graphs and session attestations recording model identity, token usage, and cost. Similarly, **Drift** (a 12-command Rust binary) replaces Git commits with immutable, content-addressable **intents** linking a goal, tree-sitter AST diffs, and full agent conversation/tool-call traces in an append-only history without staging areas, rebases, or force pushes.

### Agent-Scale Git Backends and Agentic Forges

Rather than abandoning Git syntax or LLM pre-training priors, a second cohort preserves standard `git` commands while rebuilding server storage, consistency models, and pull-request review.

**OpenAI Pando**, serving internal production traffic since April 2026 and detailed on November 2, 2026, was built in Rust in 10 weeks by one lead engineer directing teams of Codex agents, validated with deterministic simulations plus Lean and TLA+ formal models. Instead of serializing all repository writes through a three-phase commit or global write-ahead log (WAL), Pando enforces **causal consistency**: each branch ref updates independently via atomic compare-and-swap in a horizontally scalable metadata store, so parallel pushes to distinct branches never contend. The explicit trade-off is that a client reading multiple branches simultaneously is not guaranteed a single global point-in-time snapshot. To eliminate per-client pack computation and bloated ref lists, Pando advertises only a designated trunk branch by default, streams incoming packfiles straight to blob storage without unpacking, compacts packs in the background like an LSM-tree, and distributes reusable packs via Git's `packfile-uri` feature and regional caches. OpenAI reports nearly **5x (~80%) lower median push latency**, nearly **1 PB of Git data served daily** (peaking above 57 TB in one hour), and **\>99% local disk cache hit rates**, though Pando remains internal with no public code, API, or release date announced.

**Entire** (`entire.com`), founded by former GitHub CEO Thomas Dohmke and launched on October 26, 2026 after a $60 million seed round at a $300 million valuation, builds a distributed Git-compatible forge around three primitives. First, **Checkpoints** use CLI hooks to capture JSON-lines session transcripts, prompts, tool calls, and token counts—with local secret redaction—storing them on an orphan branch (`entire-checkpoints-v1`) so metadata does not pollute primary commit history. Second, **Continuous Memory** pairs `entire-brain` with `entire-graph` (both MIT-licensed alongside the CLI) to index captured sessions against a semantic code graph so subsequent agents query prior decisions instead of re-reading repositories. Third, **Trails** replace manual pull requests: on every push, independent review agents run in cloud sandboxes (Daytona and E2B) to score changes against custom evals alongside CI partners Buildkite and Depot. Using its open-source **ForgeMark** benchmark, Entire claims push throughput up to **89x faster than GitHub** (418 pushes/s) and **6x faster than Cursor Origin**, alongside up to **71% token savings** —vendor-reported figures that have not yet been independently benchmarked.

**Cursor Origin**, unveiled in June 2026 alongside SpaceX's announced acquisition of Cursor's parent company Anysphere and launched in early beta on August 17, 2026, embeds a Git forge directly inside Cursor's `Codebase` tab. Its **Continuity** storage layer treats local repository disks as disposable warm caches routed via rendezvous hashing, while persisting the canonical WAL in Amazon S3 via atomic compare-and-swap (eliminating consensus elections and relational routing tables). Cursor reports up to 120 pushes/s on S3 Standard and over 300 pushes/s on S3 Express One Zone, alongside demo figures of 296,000 clones/hour and ~22–22.6 commits/s per repository. Drawing on its December 2025 acquisition of **Graphite**, Origin includes stacked pull requests and two-way GitHub mirroring (where GitHub remains the source of truth until explicitly detached). However, as an early beta restricted to paid Cursor plans, Origin lacks public repositories, published SLAs, rate-limit guarantees, and third-party benchmark verification.

### Git-Compatible Local Layers and Semantic Merge Drivers

For teams anchored on GitHub or GitLab, a third ecosystem upgrades local branching, workspace isolation, and merge engines while preserving standard Git remotes.

**Jujutsu (`jj`)**, an Apache-2.0 tool built on the `gitoxide` Rust backend (32.5k GitHub stars), introduces automatic working-copy snapshots (`@`), stable change IDs across rebases, first-class conflict objects stored inside commits, and a repository-wide operation log (`jj op log` / `jj undo`). Because coding agents occasionally wipe untracked files via `git clean` or lose unrecorded edits across context compaction, practitioners wire `jj status` into shell `preexec` hooks or Claude Code `PreToolUse` hooks for sub-10ms recovery points. Yet `jj` carries notable operational trade-offs for agents: as of November 2026, its compatibility documentation lists Git partial clones and Git worktrees as unsupported, and agent rulebooks must strictly mandate `--no-pager`, `-m` flags, and bans on interactive TUIs (`jj resolve`, `jj diffedit`, `jj arrange`) to prevent sessions from hanging.

**GitButler (`but`)** takes the opposite local path by supporting multiple **parallel branches inside one shared working directory**, avoiding the disk, dependency-install, and dev-server duplication of separate Git worktrees. Agents operate via `--json` CLI output or a dedicated MCP server (`but mcp`), committing positional file or hunk IDs directly to independent branches or branch stacks while `but oplog` enables unlimited local undo. Its central trade-off is the absence of runtime isolation: concurrent agents share one filesystem, lockfile, and build state, requiring explicit file-ownership policies or fallback to worktrees when tasks need competing checkouts. **Meta's Sapling (`sl`)** similarly replaces branches with linear commit stacks and **EdenFS** lazy virtualized checkouts, using `sl follow` and `sl adopt` so parallel agents in separate worktrees can safely chase and restack onto commits amended by sibling agents.

To curb Layer 1 and Layer 2 merge collisions inside standard Git, **Ataraxy Labs** built **Weave** (a Rust tree-sitter entity-level 3-way merge driver configured via `.gitattributes` plus an experimental CRDT MCP coordination layer) and **Sem** (an entity-level `git diff` replacement across 28 languages). By matching functions, classes, and config keys instead of line numbers, Weave auto-merges independent edits within the same file; in Ataraxy's own tests, it achieved **31/31 clean merges versus Git's 15/31** on a synthetic multi-branch suite and **83 wins with zero regressions on C, Python, and Go across 4,917 real-world file merges**. Because Weave operates per-file, it cannot catch cross-file signature mismatches. Tackling cross-file state interference from another angle, the May 2026 **STORM** research framework enforces file-level context consistency at write time—rejecting an agent's write if the target file or any read dependency changed since observation—and outperformed isolated Git worktrees on Commit0-Lite with Claude Sonnet 4.6 (**82.5% macro / 46.2% weighted pass rate** versus **63.8% / 24.6%** for `GitWorktree` and **66.4% / 20.7%** for single-agent).

### Copy-on-Write Sandboxing and Versioned Agent Memory

Because `git worktree` shares `.git` metadata and provides no security isolation against prompt injection or destructive tool calls, teams running autonomous agent loops increasingly combine filesystem copy-on-write cloning with versioned external state stores. At the local filesystem layer, **git-cow** uses macOS APFS clones and Linux `FICLONE` reflinks to create instant independent repository copies (`git-cow copy`, with isolated `.git` directories for untrusted agents) or linked worktrees (`git-cow add`) while blocking symlink and `.git/hooks` escape vectors. **SandFS** similarly provides an `O(1)` lazy CoW sandbox filesystem via `mount()`, `fork()`, and `changes()` APIs over Python, Rust, and MCP (blocking MCP writes to `.git`). In cloud microVM environments, platforms like **Cortex** (Firecracker) and **Daytona** split large base images into immutable SHA-256 chunks served over Network Block Device (NBD) and `userfaultfd` CoW memory so snapshot storage and startup latency scale only with dirty blocks.

To prevent context loss across agent crashes and context compactions, a parallel layer applies version control to agent tasks and reasoning. **Beads** (`bd`) persists dependency-aware task graphs in **Dolt** (a Git-versioned SQL database supporting branches, diffs, and multi-writer server concurrency). Multi-agent orchestrator **Gas Town** pairs Beads with Git worktrees and routes worker branches through **Refineries** —Bors-style bisecting merge queues that serialize and verify merges into `main`. Early production deployment at DoltHub revealed significant operational hazards in autonomous swarms, however, including $100/hour peak token burn, auto-merged failing tests, and five force-pushes to `main` to recover corrupted state. In academic research, **GitOfThoughts** (June 2026) encodes LLM reasoning trees directly as Git repositories (commits as scored thoughts, `git notes` as scores, tags as outcomes); controlled evaluations found that Git delivers auditability, history, and mergeability at accuracy parity, while stored reasoning memory improved accuracy only on near-duplicate problems (cosine similarity ≥ 0.8, yielding +12 to +13.5 percentage points at cosine ≳ 0.85) rather than transferring novel problem-solving methods.

## Benchmarks, Vendor Claims, and the LLM Prior Tax

Evaluating agentic VCS tools requires distinguishing reproducible measurements from vendor-authored benchmarks, especially given that most contenders published initial numbers only in mid-to-late 2026.

The most detailed comparative CLI benchmark available is **vc-bench** (July 20, 2026), authored by GitButler to test how **Claude Opus 4.8** and **GPT-5.5** execute six complex version-control operations (selective hunk commits, multi-commit amends, splitting mid-stack commits, reordering, squashing, and rebasing dirty branches) across 360 deterministic runs with raw Git writes blocked in non-Git runs. Across the full 360-run matrix, **359 runs passed**: GitButler passed all 120 runs (running ~65% faster than Git with ~78% fewer commands overall), whereas Jujutsu recorded the sole miss and ran slower than Git. In the 60-run per-tool breakdown displayed for one agent, GitButler averaged **34.0s** and **4.5 commands** (13.3 KB output) versus Git's **92.2s** and **20.4 commands** (31.7 KB) and Jujutsu's **110s** and **21.0 commands** (46.1 KB)—establishing a statistically significant paired improvement for GitButler (−58.2s \[−106s, −10.7s\] and −15.8 commands \[−26.0, −5.7\]), while Jujutsu's delta (+17.6s \[−23.3s, +58.6s\]) was slightly slower than Git. Complementing this, TabbyML's **jj-benchmark** (63 Jujutsu tasks) revealed substantial model variance in following non-Git syntax: Claude 4.6 Sonnet passed **92%** (58/63), ahead of Gemini 3.1 Pro (**84%**, 267.6s/task) and GPT-5.4 (**81%**, 77.6s/task).

For non-Git and server-scale systems, published figures remain primarily vendor-reported. **Atomic's** January 2026 sequential stress test recorded ~1,680–1,690 changes/second across 100,000 sequential changes (~60 seconds total, implying 592–595 µs/change despite rounded "~500 µs" prose), but Atomic's own documentation notes the lack of hardware metadata, p99 latency, and concurrent multi-agent write measurements. Likewise, **Entire's ForgeMark** figures (418 pushes/s; 89x faster than GitHub), **Cursor Continuity's** 300+ pushes/s on S3 Express, **OpenAI Pando's** ~5x push latency improvement, and **Oak's** 95% snapshot speedup all derive from vendor-run tests or internal production environments rather than independent third-party evaluations.

Across non-Git platforms, developers consistently encounter an **LLM prior tax**. Because models have absorbed vast Git and `grep` corpora during pre-training, agents periodically ignore `AGENTS.md` or `CLAUDE.md` rules and revert to raw `git` commands—or trigger interactive TUIs that hang headless sessions. Practitioners mitigate this by hard-blocking raw `git` writes in harness permissions, exposing structured **MCP JSON-RPC tools** (as in GitButler, Weave, and `agentic-jujutsu`), or rewriting model tool calls at the harness layer so agents issue familiar Git commands that translate cleanly onto a non-Git backend.

## Selection Framework for Engineering Teams

Replacing Git wholesale is rarely the highest-leverage first investment outside hyperscale monorepos. Because an agent implementation that takes minutes frequently sits hours in human review and CI queues, teams should match tooling strictly to their measured bottleneck:

1. **Local parallel tasks and agent rollbacks (1–20 concurrent agents):** Keep standard Git remotes untouched. Adopt **GitButler (`but mcp`)** when parallel tasks can share one build and dev server, or **Jujutsu (`jj`)** / **git-cow** when tasks require isolated checkouts, automatic pre-command snapshots, and operation-log recovery. Configure **Weave** and **Sem** via `.gitattributes` and `git diff` to eliminate false textual conflicts and surface AST blast radii without changing agent prompts.
2. **Untrusted execution or heavy monorepo clone latency:** Combine a shared Git object cache or **Sapling/EdenFS** virtualized checkout with CoW sandboxing (**SandFS**, **git-cow copy**, or btrfs/microVM snapshots) and explicit work-in-progress caps. Avoid `jj` if workflows rely on Git partial clones.
3. **Compliance, auditability, and cross-session context loss:** Retain Git storage while attaching structured session provenance through **Entire CLI** checkpoints (`entire-checkpoints-v1`), **Beads + Dolt** task graphs, or **Atomic** if cryptographic per-turn attestations and graph provenance are hard requirements.
4. **Code review saturation and 10,000+ daily merges:** Prioritize agent-assisted pre-review evals, stacked PR workflows (**Graphite / Origin**, **Entire Trails**, or **Refinery** bisecting merge queues), and API-driven repository queries before considering custom server-side architectures modeled on **Pando** or **Scion**.
